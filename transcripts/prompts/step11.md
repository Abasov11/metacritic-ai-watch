Шаг 11 — оценка качества резюме отзывов (LLM-as-judge). Смысл: показать, что резюме не выдумывают, а опираются на отзывы. Код — `/ponytail`.

1. `app/eval.py` + CLI `python -m app.eval --limit N [--kind critic|user] [--report docs/EVAL_SUMMARIES.md]`: для каждого резюме из базы (где `model` не пустой) берёт исходные отзывы того же вида и каждый пункт `likes`/`dislikes` отдельно отдаёт судье. Судья — вторая модель, не та, что писала резюме (`google/gemini-2.5-flash-lite` или `openai/gpt-4.1-mini` — выбери и обоснуй), промпт: «подтверждается ли утверждение хотя бы одним из отзывов ниже» → строгий JSON `{supported: bool, evidence: "цитата ≤200 символов или пустая", note: "..."}`. Пункты из одной игры/вида — одним вызовом (массив утверждений → массив вердиктов), чтобы не тратить вызовы; учёт стоимости в `llm_calls` с `purpose="eval"`.
2. Метрики: доля обоснованных утверждений всего, по видам (critic/user), по знаку (likes/dislikes), список необоснованных с цитатой отзыва, к которому ближе всего. Отчёт в markdown: методика (что считается подтверждением, ограничения судьи), таблица метрик, 5–10 примеров обоснованных с цитатами и ВСЕ необоснованные, стоимость прогона, дата и модели.
3. Тесты без сети: разбор ответа судьи, подсчёт метрик на подставных данных, устойчивость к невалидному JSON.
4. Живой прогон на всех резюме в базе (сейчас их немного — те игры, у которых есть отзывы), отчёт положи в `docs/EVAL_SUMMARIES.md`, в README — абзац «Качество резюме» со ссылкой и главной цифрой. Если найдутся необоснованные утверждения — не прячь, это и есть ценность отчёта; если их окажется много — предложи правку промпта резюме, но не применяй без замера «до/после».
5. `ruff`, `pytest -q` — дословно. Коммит.
